Give the agent a result you can verify independently. Keep the reference result and its tests outside the agent's write permissions.

This page proposes a minimal verification setup for industrial ecology (IE) work done with coding agents. Treat it as a starting proposal rather than a settled norm: if a check is missing, too heavy, or a bad fit for your subfield, [push back or suggest a better one](/contribute/).

## Chat vs. agent, and what a harness is

In a **chat** interface, you send one message and get one reply back. You copy code out, run it yourself, and paste errors back in.

A **coding agent** puts a language model inside a loop with tools: it can read files, edit code, run shell commands, inspect the output, and keep iterating until it decides the task is done.

A **harness** is everything you put around that loop: the instructions file, file and command permissions, hooks that run before or after a tool call, and the tests the agent runs against. Think of the agent as a new lab member:

- **`AGENTS.md` is the onboarding document:** the few rules they cannot guess.
- **Skills are the lab protocols:** written steps for one task, read only when that task comes up.
- **Tests and automated checks (CI) are the calibration:** a known sample that must give the known answer.
- **Hooks are the safety interlock:** a rule the harness enforces, whatever the agent decides.

## Set up the harness

### Keep `AGENTS.md` short

`AGENTS.md` is a plain Markdown file at the root of a repository that coding agents read when a session starts. Keep it short. Put only what the agent cannot infer quickly from the code:

- **Check command:** linting, formatting, and type checks.
- **Fast test command:** the quickest test command to run after each edit.
- **Non-standard conventions:** units, coordinate systems, naming rules, or tools that differ from defaults.
- **Never-do list:** hard boundaries such as protected test folders or licensed data that must stay out of git.

Skip the repository overview, directory tree, and architecture prose. Gloaguen et al. ([arXiv:2602.11988](https://arxiv.org/abs/2602.11988)) found that repository context files do not generally raise task success and add more than 20% to inference cost on average. Evidence on cost is mixed: across 124 pull requests in 10 repositories, Lulla et al. ([arXiv:2601.20404](https://arxiv.org/abs/2601.20404)) measured a 28.64% lower median runtime with an `AGENTS.md` than without.

Delete lines the code no longer follows. In 40 Python projects built so that the instruction file and the code used different conventions, two coding agents followed the stale file in 90.1% of their choices (Xu and Wu, [arXiv:2610.30571](https://arxiv.org/abs/2610.30571)). One sentence telling them to follow the code, like the last convention below, raised the share that followed the code from 4.2% to 91.4%.

```markdown
# AGENTS.md

- Lint: `uv run ruff check .`
- Fast tests: `uv run pytest -q`
- Conventions: all mass flows are in kg; impact factors come from open or synthetic fixtures only.
- When this file and the code disagree, follow the code and say so.
- Never do:
  - Do not edit files under `tests/golden/`.
  - Do not commit licensed inventory data (such as ecoinvent values) to fixtures or notebooks.
  - If a test cannot pass without changing expected values, stop and report the mismatch.
```

### Few skills, each tested

Install a skill only when it helps on your own tasks, and keep one skill per job. On SWE-Skills-Bench ([arXiv:2603.15401](https://arxiv.org/abs/2603.15401)), 92 of 98 public skills had no statistically significant effect. Yan et al. ([arXiv:2610.11647](https://arxiv.org/abs/2610.11647)) found that a second skill for the same job takes one run in five away from the installed one.

### Ask for a plan first

For anything bigger than a one-line fix, ask the agent to write its plan before it edits any file. Read the plan: a wrong emission factor or system boundary is easier to catch in a short plan than in a long diff.

### One worktree per agent

Give each parallel agent its own [git worktree](https://git-scm.com/docs/git-worktree): a separate checkout of the same repository on its own branch. Their edits cannot overwrite each other, and you review each branch on its own.

Worktrees keep the files apart, not the logic. Two changes that each pass their tests can still fail once merged. Xia et al. ([arXiv:2609.25396](https://arxiv.org/abs/2609.25396)) saw this in 97% of runs on Django tasks built for the study, but in only one of 834 real pull request pairs. Telling each agent about the other's change recovered 82%.

More agents in parallel buy little. On tasks that build a whole repository, Lyu et al. ([arXiv:2611.33893](https://arxiv.org/abs/2611.33893)) found that parallel subagents (helper agents the main agent starts) raised the pass rate on hidden tests by only about 1 to 5 percentage points, at up to 3.8 times the cost of a single agent.

### Hooks for rules without exceptions

A line in `AGENTS.md` is a request: the agent usually follows it, but nothing makes it. A **hook** is a script the harness runs at a fixed point in the loop, such as before each edit or when the agent says it is done. Use hooks only for rules that have no exceptions, for example:

- before an edit: refuse any write under `tests/golden/` (see [Protect the test](#2-protect-the-test));
- after an edit: run the formatter;
- when the agent stops: run the test suite, and send the failures back if any test fails.

The hook configuration format differs per tool.

## Verify AI-assisted IE work

Most studies cited below are preprints, not yet peer reviewed.

### 1. Golden test

Pin at least one known numerical result in a dedicated test (a **golden test**) using open or synthetic factors, never licensed database values. For example, build a small matrix life cycle assessment (LCA) where you know the exact total from hand calculation, and assert the result within a tight numerical tolerance.

```python
def test_steel_bracket_gwp_golden():
    # Synthetic factors: 2.0 kg steel * 1.85 kg CO2e/kg + 0.5 kWh * 0.40 kg CO2e/kWh
    result = run_bracket_lca(mass_kg=2.0, electricity_kwh=0.5)
    assert abs(result["gwp100_kg_co2e"] - 3.90) < 1e-6
```

A script that runs can still be wrong by three orders of magnitude. A planted unit swap (`kg` vs `t`) or an impact-method swap turns this test red immediately.

### 2. Protect the test

If a coding agent can edit both the model code and the test suite, a failing golden test is not a reliable guard: the agent can make the suite green by editing the expected number, relaxing the tolerance, or skipping the test.

1. Give the agent read-only access to the canonical tests and fixtures, for example through a
   read-only mount. Apply the restriction to its shell and edit tools as well.
2. Check that the agent can run the tests and that its tools cannot write to the protected files.
3. Require a human review before changes to the protected files can merge. On GitHub, use
   [required code-owner review](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners#codeowners-and-branch-protection).
   Keep the review rule outside the agent's control.
4. Tell the agent to report the failure when the test and the task disagree.
5. Keep at least one golden case outside the agent's repository, and run it yourself.
6. Diff the test files at review, even when the suite is green.
7. When a hook or reviewer rejects the work, tell the agent only that it failed, not how you caught the shortcut.
8. Recompute the headline number yourself before you report it.

A pre-edit hook that refuses the write looks like this. Adapt how the path arrives and which exit code blocks the call to your tool:

```sh
#!/bin/sh
# $1: the file the agent wants to edit.
case "$1" in
  tests/golden/* | */tests/golden/*)
    echo "tests/golden/ is read-only. Report the mismatch instead." >&2
    exit 2
    ;;
esac
```

The hook only sees the edit tool, not a shell command that writes the same file, so keep the read-only mount from item 1 too.

Keep the abort rule, and enforce the boundary in the harness too: instructions alone do not hold. ImpossibleBench ([arXiv:2510.20270](https://arxiv.org/abs/2510.20270)) has Conflicting-SWEbench tasks whose tests contradict the task, so any pass is a shortcut. GPT-5 passed 54% of them and Opus 4.1 50%. An explicit option to abort cut GPT-5's cheating to 9% but helped Opus 4.1 far less. Read-only tests stopped Opus 4.1's main shortcut, editing the tests, but not others, such as special-casing the tested inputs. BaitBench ([arXiv:2608.30724](https://arxiv.org/abs/2608.30724)) planted a shortcut in three synthetic tabular ML tasks. Seven frontier agents took it in 57.1% of runs, and still in more than 50% on average when told not to cheat.

Passing the tests the agent can see is not enough. On SpecBench ([arXiv:2605.21384](https://arxiv.org/abs/2605.21384)), every frontier agent maxed out the visible tests. The gap to held-out tests (ones the agent never sees) grew by 28 percentage points for every tenfold increase in code size. On EvilGenie ([arXiv:2511.21654](https://arxiv.org/abs/2511.21654)), where agents could edit the test files, two of three commercial coding agents explicitly reward hacked: they made the check pass without doing the task.

Detailed rejections may help the agent hide the shortcut, the reason for item 7. When a review panel kept rejecting research agents' hacks, Huang et al. ([arXiv:2609.28614](https://arxiv.org/abs/2609.28614)) found that over five rounds agents got one past it in 40.5% of 79 model-task pairs when the rejection gave details, and in 20.3% when it was generic. The detailed feedback also included the earlier attempts.

### 3. Check the meaning, not just that it ran

For data work, a script that runs and returns a plausible number can still use the wrong indicator, unit or filter. Before the agent starts:

- Write a frozen **metadata card** for each dataset: its units, codes and classifications, and the filters that matter. Keep it read-only, like the golden tests.
- Write the **output contract** in full: columns, units, ranking key and the shape of the answer.

Then check the result against both. Necula ([arXiv:2609.22222](https://arxiv.org/abs/2609.22222)) ran one model (Claude Sonnet 5, three replicates) on 30 Eurostat tasks. The frozen metadata card raised the share of exactly correct answers from 27.8% to 51.1%. Even in the best setup, one answer in five ran without error but was wrong. Leaving the ranking key and unit out of the contract made one setup's score 23.4 points too low.

### 4. Review in a fresh session told to find bugs

Before you accept the work, give the task and the diff to a new session and tell it to find bugs, for example with the [adversarial code review prompt](/best-practices/prompts-and-skills/#adversarial-review-of-ai-written-code). Agents overrate their own work. In Kaddour et al. ([arXiv:2602.06948](https://arxiv.org/abs/2602.06948)), some agents that succeeded 22% of the time predicted 77% success. Asking them to look for bugs, not rate their success, gave the self-assessment closest to their real rate. On Terminal-Bench, across seven frontier coding models, Zhang et al. ([arXiv:2610.34577](https://arxiv.org/abs/2610.34577)) found that review by a separate agent (a critic) raised average accuracy by 5.9 to 9.5 percentage points, at 1.13 to 1.25 times the cost without review.

Count a test the agent wrote only if it asserts a number you derived another way: by hand, from a published table, or with a second method. Banik et al. ([arXiv:2606.18168](https://arxiv.org/abs/2606.18168)) found that 80.2% of 86,156 agent-written test patches have weak or no explicit oracle signals (assertions that check the result).

### 5. Claim ledger (existence checks are not claim checks)

Automated reference tools can check whether a DOI resolves or whether a title appears in Crossref or OpenAlex. That checks **existence**, not **meaning**: a real paper can still be cited for a claim it does not make, a number from a different boundary, or a conclusion the authors qualified.

One reference sweep on an AI-assisted draft shows the gap. All 64 references passed the existence check. Four of them, cited for claims that reached the draft, were then checked against their PDFs, and all four had been mischaracterized. That is one sweep of one draft: an example of the failure mode, not a rate.

Larger studies show the same gap. Across 14 models writing reports with citations, Onweller et al. ([arXiv:2605.06635](https://arxiv.org/abs/2605.06635)) found that even the strongest kept more than 94% of links valid but got only 39 to 77% of facts right. In a peer-reviewed randomized trial, 288 researchers tried to reproduce published social science results. Brodeur et al. ([PNAS, 2026](https://doi.org/10.1073/pnas.2524747123)) report that human-only teams reproduced 94%, AI-assisted teams 91% and AI-led teams 37%, with the AI teams using ChatGPT. The authors call the AI-led figure a lower bound on what AI can do.

Keep a plain **claim ledger** beside any AI-assisted manuscript or report: one row per cited claim, filled in only after opening the primary source.

### 6. Log the run

Log one row per run, so the cost of AI-assisted work is on record next to the result. Include the date, task, model, input and output tokens, and API cost.

```csv
date,task,model,input_tokens,output_tokens,cost_usd
2026-11-18,refactor-matrix-solver,example-model,42100,6800,0.23
```

Report tokens and cost directly from the runner or provider logs. Only report energy use or greenhouse gas emissions when backed by a primary source you have read (such as a documented measurement study or provider methodology), not by multiplying token counts by an unverified rule of thumb.
